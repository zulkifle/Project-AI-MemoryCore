## EMV/Card Scheme Ground Truth (2026-08-25)
*Found by reading old project documentation (`documentation/Card structure/` and `documentation/Technical Spec/`) in response to Zul asking whether the signature gets written to a physical chip. This resolves several open questions from earlier research/design sessions with actual source documents instead of inference from the C++ code alone.*
- **This is a real Petronas fleet/fuel card program**, not a generic internal system: card classes are Vehicle, Driver, Fleet Manager, Standalone, and **National Fuel Subsidy** (with an explicit `MDTCA` — Ministry of Domestic Trade and Consumer Affairs — reference for the government fuel subsidy card type). Confirms cards are genuinely used at fuel-purchase terminals (Zul's "guna kat pump" framing was correct, though it was an assumption at the time it was made, not yet confirmed by a document — it's confirmed now).
- **"SSAD" is not an undocumented in-house acronym** — it's officially **"Signed Static Application Data,"** the real EMV term. It was simply never spelled out inside the C++ source itself (matching the earlier Security Review Findings observation that the crypto logic was "undocumented," not deliberately obscured) — the documentation existed all along, just in old Word docs no one had cross-referenced against the code yet.
- **The signature genuinely gets written into the physical smart card chip**: "The issuer certificate and MSG-2 will be stored inside the smart card," and card data is "prepared by **SAPURA** and certified... before the data can be injected to the smart card" (SAPURA appears to be the card personalization/chip-injection bureau). The terminal authenticates the card **offline** by reading this data from the chip — this is genuine **EMV SDA (Static Data Authentication)**, not a proprietary Petronas scheme.
- **The exact padding formula is confirmed EMV-standard, not invented**: the docs give `SSAD = SIGN(CA_Pvk(0x6A | ...))` — the `0x6A` header byte is literally the official ISO/IEC 9796-2 message-recovery signature scheme marker, matching `Iso9796LikePaddingCodec.TRAILER_START` byte-for-byte. This is strong independent confirmation that the padding logic reverse-engineered from `Task.cpp`/`HSM.cpp` earlier was reproduced correctly.

## New Embossing Format Findings (2026-08-25)
*Zul forwarded a real client email from Izzuddin (PETRONAS Dagangan Berhad Digital) about planning a UAT for the new embossing file format for one PDB card product, plus a genuine sample: `CardSys.A.260714.zip` (uploaded, 3 files: `NRCCC20260116_1.A.260714`, `NRPOC20260116_1.A.260714`, `NRPRC20260116_1.A.260714`). Extracted and analyzed structurally (offsets/lengths only — no full PAN/track data logged here).*
- **Pipeline is 3-party, not 2** (per the email — confirms and extends earlier understanding): **CTS** generates the embossing file → **Cardsys** processes it (explains the `CardSys.*.zip` filename — it's literally named after this system) → **MSC Trustgate** (us) signs it. Useful for knowing where in the chain a given data issue could originate — a "new value" complaint could come from CTS's generation logic or Cardsys's processing step, not necessarily something Trustgate's signing side has any control over.
- Izzuddin's email also asks whether the UAT file transfer must go through the existing SFTP channel or can use an alternative secure method — this is a Trustgate/PDB operational logistics decision, not a technical question for this project file; not tracked here.
- **File length is 395 bytes/record, but the card DATA is unchanged — corrected finding (2026-08-25, superseding an earlier same-session claim)**: initial analysis suspected a data field had grown by 1 byte. Full field-by-field verification against `Cardsys Data.docx`'s exact byte-level breakdown of the old 394-byte layout (header 204 + Track1 152 + Track2 38, every sub-field length confirmed) proved **every single field in the new sample is byte-for-byte identical** to the old format, at the exact same offsets, with zero exceptions. The 395th byte is a **trailing `\r` (0x0D, carriage return)** — confirmed present after *every* record boundary in all 3 new files (13 records checked, 100% consistent, zero exceptions: byte at record-relative offset 394 is always `0x0D`). So the real change is **CR-delimited records** (`394-byte record` + `\r`, repeated) replacing the old format's records with **no delimiter at all** (pure back-to-back concatenation, confirmed from the 2026-08-24 old sample) — not a card-data field change. This is fully consistent with the BRS's own claim that "the overall embossing file structure remains unchanged," since the *card data* genuinely hasn't changed — only the file's record framing has.
- **Fix implication**: `CardRecord`/the file-extraction logic needs to split records by `\r` (or strip a trailing CR after each 394-char chunk) rather than assuming pure fixed-width concatenation with no delimiter. This is a much smaller change than the earlier (wrong) "a field grew by 1 byte, offsets shift" theory would have required — no `CardRecord` offset constants need to change, only the record-splitting logic upstream of it.
- **New tag value found: `NRCC`.** Decodes (via the same hex-tag scheme `CardRecord` already uses) to `N`+`R`+`C`+`C` — Stage Code `NR` (New+Replacement, known) + Payment Mode `CC` (**not defined** in the old `BRS_Embossing File Format.pdf`, which only documents `PO`=Postpaid/`PR`=Prepaid) + Card Type `C` (Chip, known). This remains a genuine, independent new-value issue — `CardRecord.NEW_ISSUE_TAGS` doesn't include this tag, so it would be rejected as "unrecognized issue-type tag" today.
- **Actionable next step**: draft a specific, evidence-backed question back to Izzuddin/PDB Digital — e.g. "we confirmed the card-data fields are unchanged; the file now has a trailing CR after each record (was unseparated before) and includes an unrecognized `CC` payment-mode tag — can you confirm both are intentional and what `CC` represents?" Sharper than the original generic Pre-BRS "send us the spec" request.
- **Still open**: whether the CR-delimiting is an intentional new file convention from Cardsys/CTS or an artifact of how this particular sample was exported/emailed (worth asking explicitly rather than assuming); what `CC` payment mode means functionally; whether other new values exist beyond these two. The `"Invalid Len [129]"` rejection seen in the 2026-08-24 old-format sample is likely unrelated to either of these (that sample was confirmed old-format, no CR framing, no NRCC tag).

## Signing Parity Verified Against Real Production Data (2026-08-25)
*Zul asked directly: will Java and C++ produce the same signing result? Answered with an actual verified test, not a theoretical argument.*
- **`.ssd` report line format cracked**, from `GenerateSSAD.cpp`'s `ReportSSAD` (line ~809-828): `fprintf(pFile, "%s %s %02d %s %s\n", SeqNo, CardNo, Root, Cert, SSAD)`. For a 1408-bit key, arithmetic confirms the **signature is exactly the last 352 hex characters** of the line — everything before that (SeqNo, CardNo, Root, and a 512-hex-char issuer certificate blob) is not signature data. This resolves the "composite format, not pure hex" gap flagged back on 2026-08-24.
- **Message-to-sign construction confirmed exactly** from `GenerateSD()` (`GenerateSSAD.cpp:226`): `sprintf(szSDData, "%02d%s%s", Root, Track1hex, Track2hex)`, hex-decoded — i.e. **1 raw byte (root indicator, always `0x01` in production) + Track1 (76 bytes) + Track2 (19 bytes) = 96 raw bytes.** Matches the existing `CardSigningService` javadoc's "root-indicator + Track1 + Track2" claim exactly, byte-for-byte, no correction needed.
- **Real verification performed**: took record #1 from the real 2026-08-24 old-format sample (`NRPOC20260822_1.A.260824`) and its real corresponding signature from `NRPOC20260822_1.A.260824.ssd`. Built the expected pre-sign buffer using this project's own `Iso9796LikePaddingCodec`, then did a raw RSA **public-key** "verify" (the mathematical inverse of the private-key sign operation — needs no private key) against the real signature, trying every issuer `pm_certificatemaster` shows was ever used in production (10 candidates, moduli/exponents from `pm_tokenissuer`). **Issuer #11 matched exactly** — recovered buffer byte-for-byte identical to the Java code's own computed pre-sign buffer, full structural validation (trailer/padding/hash) passed. Issuer #11 is also the most recently onboarded issuer, consistent with the project's earlier "Key Usage" finding that current traffic concentrates on the newest issuer(s).
- **Conclusion**: the Java signing core (`Iso9796LikePaddingCodec`, and by extension `HsmRsaSigningService`/`LocalKeyRsaSigningService` which use it identically) is confirmed to reproduce the legacy C++ system's actual real-world output exactly, not just internally self-consistent test coverage. This is the strongest correctness evidence the project has to date.
- **Made permanent**: `SigningParityTest` (`src/test/java/.../signing/SigningParityTest.java`) — runs this exact check on every `mvn test`, using the real Track1/Track2/signature checked in as fixtures at `src/test/resources/parity/record1-{track1,track2,signature}.hex`. Issuer #11's real public modulus is embedded in the test as a documented constant (public key only, not sensitive).
- **Caveat**: this verifies the *current, old-format* record structure only. Once `CardRecord`/`CardRecordExtractor` are updated for the new format (CR-delimiting, `NRCC` tag), a second parity test against a real new-format signed sample (once available — the `TG.*` output for `CardSys.A.260714.zip` hasn't been provided/found yet) would be the natural next verification milestone.
- **⚠️ Correction to the "closed system" assumption**: the embossing file spec also references **"Visa PVV"** (Visa PIN Verification Value) as a Track 2 field — meaning these cards are very likely **Visa co-branded**, not a fully closed system Petronas alone controls end-to-end. This walks back the "closed system, Petronas kawal reader sendiri" answer given earlier in the same conversation (which was the best available answer *before* this documentation was found) — if the cards must stay Visa/EMVCo-compliant, the signing algorithm for the actual card SSAD is constrained by that external card scheme, not just by Petronas's own terminal fleet. **Conclusion: RSA stays for the Petronas card SSAD itself, full stop — not a Java-migration design choice, an external card-scheme compliance requirement.** The crypto-agile design (algorithm-agnostic `issuer_keys.public_key`, pluggable `CardSigningService`) is still worth keeping for other parts of the system (e.g. the PAN-at-rest AES encryption, or if a genuinely separate closed-loop product is built later), just not for this specific SSAD signature.

## Daemon Wrapper Implemented (2026-08-26)
*Built after tracing `Petronas.cpp` in full (previously only its `main()` location was confirmed) to get the exact main-loop gating logic, TCP health-check protocol, and zip-handling approach.*
- **Main loop confirmed to be a wall-clock gate, not a fixed-delay timer**: `while(i_Flag) { KeepLog(); ProcessSignal(50); ProcessTask(); }` (`Petronas.cpp:167-176`) — a tight poll loop (up to 50ms per tick) where `ProcessTask`'s real work only runs once `strcmp(currentTime, sz_TaskNextUpdate) >= 0`; after running, the next allowed time is recomputed as `now + intervalMinutes`, bumped by 59s, then truncated to the minute (the legacy format has no seconds field) — always rounds the gate *up*, never down, so truncation can't cause an early fire. `intervalMinutes` comes from `Petronas.ini`'s confusingly-named `[System] Database` key (real value: 60 — nothing to do with the database despite the name).
- **TCP health-check protocol confirmed byte-exact** (`ProcessSignal`, `Petronas.cpp:416-488`; `TestHSM`, `HSM.cpp:769-801`) — corrects the prior placeholder note: exact-match `"TESTHSM"` request → exactly `"ALIVE"`/`"DEATH"` (5 raw bytes, no terminator); anything else → current datetime `yyyy/MM/dd HH:mm:ss` (exactly 19 raw bytes, no terminator). **Important correction**: `TestHSM` doesn't check a flag — it builds a synthetic pre-sign buffer and attempts a *real* sign operation, ALIVE only if that succeeds. The Java version preserves this intent (a real sign attempt) via a caller-supplied probe rather than replicating the exact synthetic buffer, since this project's `CardSigningService` only exposes the full message→sign flow, not a raw-buffer-only entry point — documented as a deliberate, minor deviation in `HealthCheckServer`'s Javadoc.
- **Zip handling confirmed shell-based in the legacy** (`unzip` for inbound, `SSAD.cpp:300-312`'s `zip`+`mv` via a generated script for outbound) — confirms `java.util.zip` was the right call already made; no new information changed that plan.
- **Built**: `ZipUtility` (`archive` package, new — extract/create using `java.util.zip`, with zip-slip protection added as an incidental security improvement the legacy shelled `unzip` never had), `NextRunGate` (`service` package — the wall-clock gate arithmetic above, fully unit-tested including exact rounding behavior), `HealthCheckServer` (`service` package — the TCP protocol above, tested end-to-end with real sockets against `localhost`), `BatchCycleRunner` (`service` package — the full per-cycle orchestrator: resolve config → connect inbound SFTP → for each `CardSys.*.zip` → download → extract → `CardFileProcessor` per extracted file → write `.ssd`/`.err` reports → track in DB (`BatchRepository`/`BatchFileRepository`/`RejectedRecordRepository`) → zip outputs → upload with verification), and `PetronasDaemonApplication` (root package — the actual `main()`, wiring DB/SFTP config, the health-check listener, and the gated main loop together).
- **Verified end-to-end, not just compiling**: `mvn package` produces a real runnable shaded jar (`target/petronas-java.jar`, `Main-Class: com.msctrustgate.petronas.PetronasDaemonApplication` confirmed in the manifest); running it fails with `ConfigurationException: Required environment variable 'PETRONAS_DB_HOST' is not set` — the *correct* failure at the *correct* point, proving the wiring from `main()` through config-loading is real, not just theoretically compiling. 35 tests total (up from 24), all passing.
- **Deliberately not reproduced**: `KeepLog()` (daily log-file archival, unrelated to card processing — low priority, not built), and any graceful-shutdown signal handling (the legacy has none either, confirmed by the same trace — matching that, not a gap).
- **Deliberately deferred, documented as approximations rather than exact replicas**: the precise legacy `DB_SetFlagMaster` 3-variant flag-transition timing (this project marks each stage complete once its work is actually done — functionally equivalent, not state-machine-identical); `DB_FixFlag3`-equivalent startup recovery for stuck `'P'` flags after a crash (a real gap — directly relevant to the known record-3069 stuck-batch bug from the sibling C++ project, since that bug is exactly a flag left stuck at `'P'` that recovery logic should catch and doesn't).
- **Not yet run against a live environment** — no test DB/SFTP server/real key file available in this session. The next real validation milestone is running `BatchCycleRunner` against a test/sandbox DB+SFTP with a converted PKCS#8 local key file, once those are set up.

## Security Review Findings (2026-08-24)
*Line-by-line review of `SSAD.cpp`, `HSM.cpp`, `Task.cpp` (signing flow + `RunShell`), `DB2.cpp` (credentials). Each item: risk + what the Java rewrite should do.*

**Critical**
- **Shell-injection-by-design pattern** — `RunShell` (`Task.cpp:1761-1785`) does `vsprintf` into a fixed 2052-byte buffer (no bounds check — stack overflow if the formatted command exceeds it) then `system(szCmd)`. Called with unsanitized interpolated data from multiple sites: `SSAD.cpp:312` (`zip` compress), `SSAD.cpp:463` (`manual_verify.sh`), `HSM.cpp:588`/`731` (`openssl1 rsautl`). → Java: never build shell command strings; call SunPKCS11/JCE directly for crypto so shelling out for signing is eliminated entirely; use `ProcessBuilder` with an arg array (no shell) for anything that must still shell out.
- **Non-HSM fallback signs with disk key** (`HSM.cpp:553-619`, `i_HSMFlag==0`) — reads `issuer%d.key` off disk, signs via `RunShell`→`openssl1 rsautl -sign -raw`. Live path in the production binary; if `i_HSMFlag` is ever misconfigured, production silently signs with a weaker file-based key instead of the HSM. → Java: do not implement this fallback in the production build at all; any offline/test signer must live in an obviously-separate, non-production harness.

**High**
- **Filename injection into generated shell scripts** — `SSADProcess2` (`SSAD.cpp:293-312`) embeds ingested card-data filenames unescaped into a `zip` command written to `ftp_compress.sh` and executed; same pattern in `VerifySSAD2` (`SSAD.cpp:433-463`). Worth confirming against FTP-ingest naming before the Java port locks its file-naming, but the pattern itself is a real injection surface. → Java: `java.util.zip` directly, never assemble executable scripts from ingested data.
- **Unbounded `fread` into fixed stack buffer** (`HSM.cpp:604,747`) — `unsigned char szuData[516]` filled via `fread(szuData, 1, iSize, pFile)` with no check `iSize <= 516`. Only reachable via the non-HSM fallback above — disappears once that fallback is dropped.
- **Signing temp files left on disk** (`HSM.cpp:570-611`) — `data.in` (plaintext signing input) and `data.hex` (raw signature) written to a fixed, predictable filename, never deleted, reused across calls (race/overwrite risk under concurrency). → Java: keep signing data in memory only.
- **Plaintext DB credentials** (`DB2.cpp:65-117`, `DB_ReadConfig`) — MySQL host/user/password read straight from `Petronas.ini`, cleartext. → Java: environment variables or a secrets manager, never a plaintext config file.

**Medium**
- **SQL via printf-style interpolation, not parameterized queries** (`DB2.cpp` multiple sites: lines 172,191,205,268,287,301,338,358+). Values look server-generated today (dates/IDs), not directly attacker-controlled, so live exploitability looks low — but it's a landmine for any future change. → Java: `PreparedStatement` with bind parameters everywhere, no exceptions.

**Low / confirmed-correct-as-is**
- **Raw RSA via `CKM_RSA_X_509`** (`HSM.cpp:509,651`) with only the hand-built ISO/EMV-style padding for structure, no OAEP/PSS — almost certainly mandated by the card-scheme SSAD spec, not a bug. → Java: preserve bit-for-bit, document with named constants + spec reference so nobody "fixes" it into PKCS#1v1.5/OAEP and breaks interop.
- **`Login()` with empty PIN** (`HSM.cpp:424-443`, `C_Login` with `pbPassword=NULL`) — correct for a Luna PED-protected partition (physical PIN entry, not software PIN). → Java: SunPKCS11 config must assume PED hardware PIN, not a software PIN.
- **`DumpObject`** (`Task.cpp:1728-1758`) builds a hex/ASCII dump of signing input/output, but its log call is currently commented out — inert today. Latent risk if ever re-enabled (would dump card track data + HSM output in cleartext). → Java: don't build an equivalent signing-data dump utility; if tracing is ever needed, redact PAN/key material by design.
